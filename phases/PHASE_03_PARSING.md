# PHASE 3 — Parsing & Normalization

## Context
Phase 2 stores raw frames without loss. This phase turns them into structured events.
**Constraint 4 in CLAUDE.md governs this phase: always keep the raw bytes, including
for messages that fail to parse.**

## Objective
RFC 3164 and RFC 5424 parsing into the canonical schema, with a graceful failure path
and an extractor pipeline.

## Build
1. `Rfc5424Parser` — priority, version, timestamp, hostname, app-name, procid, msgid,
   structured data (multiple SD elements, escaped values), message. Store structured
   data as JSON in `structured_data_json`.
2. `Rfc3164Parser` — priority, BSD timestamp (no year — infer, handling year rollover),
   hostname, tag/pid, message.
3. `MessageParser` facade — try 5424, fall back to 3164, fall back to `raw`. On `raw`,
   still populate `source_ip`, `received_utc`, `raw_message`, and route to the
   **Parse Failures** stream. Never discard.
4. Facility/severity decoding from the priority value, with bounds validation.
5. Encoding handling: UTF-8 with BOM detection, latin-1 fallback, and a configurable
   maximum message length with truncation recorded as a field rather than a silent cut.
6. **Extractor pipeline**, ordered stages, configurable per source or stream:
   GROK → regex named captures → key-value → JSON → lookup table → rename/coerce/drop.
   Results land in `event_fields`.
7. **Parser packs — the core eight** named in `VENDOR_SUPPORT.md`, in
   `src/VSoftSol.Syslog.Ingestion/Patterns/<vendor>/`. Patterns are plain text files
   **loaded at runtime, not compiled in** — adding a vendor must be a file drop, never a
   release. Ship: Cisco IOS/IOS-XE, Cisco ASA, FortiGate, Palo Alto PAN-OS, Juniper
   JunOS, MikroTik RouterOS, Ubiquiti UniFi, and Linux (`sshd`, `sudo`, `cron`, `kernel`).
   Note the format differences called out in `VENDOR_SUPPORT.md`: FortiGate is key-value
   (use the KV parser, not GROK) and Palo Alto is positional CSV that differs per log
   type (parse by type, not one pattern).
7a. Handle every item in the **"Known compatibility traps"** section of
   `VENDOR_SUPPORT.md` — Cisco sequence numbers and `%FACILITY-SEVERITY-MNEMONIC`
   extraction, ASA numeric message IDs, ambiguous local timestamps, multi-line messages
   arriving as separate datagrams, and oversized messages. Each needs a fixture and a
   passing test.
8. **Deduplication window**: identical message + same host within N seconds increments
   `occurrence_count` instead of inserting a new row. N configurable, default 0 (off).

## Do not build in this phase
The UI pattern tester (Phase 5), stream routing (Phase 6), rules (Phase 7).

## Tests to write first
Build `tests/fixtures/messages/<vendor>/` with **at least 10 samples per vendor and 200
total across the core eight**, each paired with its expected parsed output. Then:
- Field-by-field assertion for every fixture.
- Assert `raw_message` is byte-identical to input for 100% of fixtures, parsed or not.
- Malformed-input suite: truncated priority, missing timestamp, oversized message,
  invalid UTF-8, empty payload — each must produce a stored `raw` event, never an exception.
- Year-rollover test for RFC 3164 timestamps on 31 Dec / 1 Jan.
- Dedup test asserting `occurrence_count` increments and no duplicate row is created.

## Validation & Evidence (per `TESTING_STANDARDS.md`)

- **Differential / oracle testing** — run the full fixture corpus through `rsyslog` or
  `syslog-ng` (in a container or WSL) and compare extracted fields against ours. Any
  divergence is either a bug or a documented deliberate difference; there is no third
  option. This is the strongest correctness evidence available for a parser.
- **Property-based (FsCheck)** — for any generated byte sequence: the parser never
  throws, never hangs, always returns a result, and `raw_message` is always byte-identical
  to the input. Run 10,000 cases minimum.
- **Fuzz** — truncated priorities, missing timestamps, invalid UTF-8, embedded nulls,
  1MB messages, deeply nested structured data, ANSI escape sequences, and messages
  crafted to trigger regex backtracking. Assert every pattern has a timeout.
- **Mutation testing** — Stryker.NET on the parser and extractor pipeline,
  **≥ 70% mutation score**. Coverage alone will not catch a parser that assigns the right
  field to the wrong name.
- **Per-vendor corpus** — ≥ 10 fixtures per vendor, ≥ 200 total across the core eight,
  each with expected output committed. Every trap in `VENDOR_SUPPORT.md` has a fixture.
- **Regression** — re-run the Phase 2 ingest benchmark and chaos suite. Parsing sits in
  the hot path; a throughput drop over 10% blocks the phase.
- **Evidence:** oracle comparison report, mutation score, fuzz seed log, throughput
  before/after parsing.

## Security Validation (per `SECURITY_STANDARDS.md`)

- **Log injection / forging suite** — this is the signature attack against a syslog
  collector. Messages containing CRLF, embedded newlines, fake priority prefixes, forged
  hostnames, and null bytes must **not** produce multiple stored events, must not overwrite
  the observed `source_ip`, and must not corrupt neighbouring records. The wire-observed
  source IP always wins over any hostname claimed inside the message; assert this.
- **ReDoS** — every user-authorable pattern compiles with a mandatory timeout. Feed the
  known catastrophic-backtracking corpus; assert the timeout fires and ingestion continues.
- **Memory exhaustion** — deeply nested structured data, 10,000 SD elements, a single
  1MB field, 100k `event_fields` from one message. Assert bounded allocation and a
  configured cap.
- **No sanitization on ingest** — assert that a message containing `<script>`, `=cmd|`,
  and `../../` is stored **byte-identical**. Neutralising it here would destroy evidence;
  encoding happens at render. Make this an explicit passing test so no later phase
  "fixes" it the wrong way.
- **Evidence:** log-forging matrix, ReDoS timeout proof, allocation bounds, raw-preservation
  assertion for hostile payloads.

## Definition of Done
Standard DoD, plus: 100% raw retention proven, and the post-parsing throughput number
recorded in PROGRESS.md.
