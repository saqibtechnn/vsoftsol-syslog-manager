# ADR 0021 — Self-update check and verified download

## Status
Accepted — v1.1.

## Context
The vendor asked for the application to check `github.com/saqibtechnn/vsoftsol-syslog-manager`
for new releases and make them available to install. Fully unattended self-update (download
+ silently replace the running binaries + restart the service) is not possible without
adding a new elevated helper component: ADR 0006 gives the running service a least-privilege
virtual account (`NT SERVICE\VSoftSol Syslog Manager`) with no rights to write `Program
Files`, no SCM self-control, and no broad `HKLM` write — the same wall this project already
hit with live data-directory relocation, which was scoped down rather than solved by adding
a privileged component. This ADR makes the identical call for self-update: no new elevated
helper, no expansion of ADR 0006's threat model.

## Decision 1 — check, download, and verify automatically; the Administrator installs manually
The service periodically checks GitHub, downloads a new release's manifest and (if it
verifies and is newer) its MSI, and hash-verifies the MSI — all automatically, all before an
Administrator ever sees anything. Installing is a manual, one-click-download-then-run-
elevated step, identical in kind to every upgrade this product has ever had. This was an
explicit, deliberate choice among three options (fully silent, download-and-verify-then-
manual-install, or check-only) — download-and-verify-then-manual-install, because it removes
the "did I remember to check for updates" burden without requiring a new privileged
component or changing what the service account is allowed to do.

## Decision 2 — one compile-time-baked trust anchor, not trust-on-first-use
Config bundles (ADR 0019) use trust-on-first-use: an Administrator accepts an unknown
signer's fingerprint the first time they see one, appropriate for point-to-point transfer
between an operator's own installs or a vendor pack where the recipient is meant to choose
who they trust. Self-update does not have that shape — there is exactly one legitimate
signer (the vendor), decided once, not whichever key happens to arrive with the first update
manifest a compromised distribution channel could serve. A manifest that carried its own
public key would let a forged manifest "verify" against itself, proving nothing. So the
manifest carries no key of its own; the product trusts exactly the one ECDSA P-256 public
key baked into it at build time (`ReleaseSigningInfo.PublicKeyBase64`, generated by
`build/releasesigning.targets` from `release-signing/public-key.txt`). The private half
never touches this repository, this build, or CI — it lives in the vendor's own offline
custody and is used only through `tools/VSoftSol.Syslog.ReleaseSigning`'s `sign-release`
subcommand, once per published release.

A build with no real key configured (`release-signing/public-key.txt` missing or blank —
the default in this repository, since no production keypair has been generated) bakes in a
freshly-generated-and-immediately-discarded placeholder key and sets
`ReleaseSigningInfo.HasRealKey = false`. `UpdateChecker` checks this flag before ever
contacting GitHub and fails closed — "no release-signing key is configured in this build" —
rather than silently attempting to verify against a placeholder that could never match a
real signature anyway.

## Decision 3 — manifest signing, not raw-binary signing
The release-signing tool signs a small `UpdateManifest` document (format version, semantic
version, the MSI's SHA-256, its download URL, a release-notes URL, a publish timestamp) —
not the ~12 MB MSI itself. `UpdateSignatureVerifier` verifies the manifest's signature first;
only if that passes does `UpdateChecker` download the MSI and independently re-hash it
against the manifest's pinned `MsiSha256`. Two independent checks, and the expensive one (a
12 MB download) never happens unless the cheap one (a small signed document) already passed.
The MSI's hash is checked a *third* time, immediately before the Settings page serves it to
the Administrator (`UpdateAdminService.GetVerifiedDownloadAsync`) — defense-in-depth against
the staged file being modified on disk between the check and the download, the same
discipline already applied before restoring an archive (ADR 0018/B5).

## Decision 4 — GitHub Releases' one redirect hop is allow-listed and re-validated, not blanket-refused
`WebhookExecutor` (Phase 7, B4) refuses every redirect outright — `AllowAutoRedirect =
false`, a 3xx is a hard failure. GitHub Releases assets are actually served via exactly one
redirect to a CDN (`objects.githubusercontent.com`), so that policy would make asset
downloads simply not work. `GitHubUpdateClient` instead follows **at most one** hop, and
before doing so re-validates the resolved `Location`'s host against a small fixed allow-list
(`github.com`, `objects.githubusercontent.com`) and its resolved address against the same
private-network/SSRF guard the webhook action already relies on. The GitHub API call itself
(`releases/latest`) never redirects for this endpoint and gets no exception — a redirect
there is treated as a hard failure, matching `WebhookExecutor`'s discipline exactly.

## Decision 5 — the SSRF guard is a deliberate, documented duplicate, not a shared reference
The obvious move — promote `PrivateNetworkGuard.IsBlocked`/`CheckAsync` out of
`VSoftSol.Syslog.Rules.Actions` into `Core` so both `Rules` (for the webhook action) and the
new `Data`-layer `GitHubUpdateClient` can share it — was the first draft of this design and
was **wrong**, caught by this repository's own architecture fitness tests before it ever
merged:

- `CoreArchitectureTests.Core_HasNoDependencyOn_SystemDataOrSystemNet` forbids *any* IL
  reference to `System.Net`/`System.Net.Sockets` in `Core`, not just actual socket I/O —
  `IPAddress`/`AddressFamily` themselves live in `System.Net`, so the guard cannot move
  there.
- The next attempt — leave the guard in `Rules` and add a new `Data → Rules` project
  reference so `GitHubUpdateClient` could call it directly — passed a narrower check (no
  circular reference between `Rules` and `Data`) but was **also wrong**:
  `LayeringTests.Layer_DoesNotReference_ForbiddenAssemblies` explicitly lists
  `VSoftSol.Syslog.Rules` as a forbidden reference for `VSoftSol.Syslog.Data`. This surfaced
  as a real, observed test failure (1 of 1113 unit tests red) when the full suite ran after
  wiring the reference — not a hypothetical caught by inspection.

The resolution: `VSoftSol.Syslog.Data.Updates.PrivateNetworkGuard` is a small, deliberate,
documented duplicate of the `Rules.Actions` type of the same name — same blocked-range
logic (loopback, RFC1918, CGNAT, link-local/cloud-metadata, IPv6 unique-local), same
`internal` visibility, doc-commented to point at this ADR and at the two fitness tests that
make the duplication necessary rather than a shortcut. `UpdateChecker` itself — which needs
`NotificationSink` (also a `Rules.Actions` type) to raise "update ready" / "signature failed"
notifications — could not live in `Data` for the identical reason, so it lives in
`VSoftSol.Syslog.Service.Hosting` instead, alongside every other `NotificationSink` consumer
(`SelfMonitoringService`, `RetentionTieringService`, `ReportSchedulerService`,
`AlertEvaluationService`, `ActionDispatchService`) — `Service` and `Web` are the two layers
CLAUDE.md's "dependency direction is strictly inward" rule exempts ("`Web` and `Service` may
reference anything"), so this is not a new pattern, just the first time self-update's own
orchestration needed it. `Web`'s `UpdateAdminService` already references `Service` (it always
has, for the shared composition root — ADR 0005/0020), so calling `UpdateChecker.RunOnceAsync`
directly for the "Check now" button needed no new reference either.

## Decision 6 — the enabled toggle and interval are DB-backed, bootstrap facts are not
`GitHubUpdateOptions` (which repo, asset filenames, timeouts) is bootstrap-tier —
compiled-in product facts bound from `appsettings.json`, not something an Administrator
edits. The enabled/interval toggle is a genuinely live-editable setting
(`update_settings`, migration 011), matching `ReportSmtpSettings`'s existing pattern:
CLAUDE.md Constraint 7 requires everything configurable to live in the database and be
editable from the web UI with no restart. `UpdateCheckHostedService` re-reads the interval
from the database every tick, so a changed interval — or a freshly-enabled toggle — is
picked up on the next tick, not only after whatever the old interval happened to be.

## Decision 7 — no new named interface/seam
Per CLAUDE.md's "two seams only" convention (`ILogRepository`, `IAuthenticationProvider`),
`GitHubUpdateClient` takes a plain `HttpClient` registered via ASP.NET Core's own
`services.AddHttpClient<GitHubUpdateClient>()`, not a bespoke `IUpdateHttpClient`
abstraction — tests point it at a local `HttpListener` fixture (`HttpSink`, already shared
with `WebhookSsrfTests`), the same pattern every other outbound HTTP path in this codebase
already tests against.

## Consequences
- This is the product's first genuinely internet-facing outbound path (B6 in
  `THREAT_MODEL.md`) — off by default, and even enabled it never installs anything itself.
- No key-rotation mechanism exists in v1. One embedded public key, generated once. A
  compromise or loss requires shipping a full product update (with a new baked-in key)
  through this same mechanism, verified against the *old* key one last time. Accepted,
  documented residual risk — see `release-signing/README.md`'s "Key rotation" section and
  `THREAT_MODEL.md`'s B6.
- Version-source unification (`Directory.Build.props`'s `VersionPrefix` vs.
  `installer/Installer.wixproj`'s independent `ProductVersion` literal) is not fixed by this
  feature — both must be bumped by hand for every release, documented as an explicit
  checklist step in `tools/VSoftSol.Syslog.ReleaseSigning/README.md` rather than silently
  left for someone to discover.
- No CI-assisted release automation. The private key must never touch CI, so every release
  is cut by hand, offline, by whoever holds the key — the same posture MSI builds already
  had before this feature existed.
- `VSoftSol.Syslog.Data.Updates.PrivateNetworkGuard` must be kept in sync by hand with
  `VSoftSol.Syslog.Rules.Actions.PrivateNetworkGuard` if the blocked-address logic ever
  changes (e.g. a new cloud-metadata range) — both files' doc comments point at each other
  and at this ADR as the place to look when one changes.
